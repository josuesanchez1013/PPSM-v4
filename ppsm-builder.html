PPSM Builder — Guide

A single, offline tool that turns scan outputs into a Ports, Protocols & Services Management (PPSM) register. Everything runs in your browser — nothing is uploaded, nothing needs the internet. Safe for standalone / air-gapped use. It assembles a register from the DoDI 8551.01 data model; it does not certify compliance — accuracy of inputs and the boundary / classification analysis remain yours.

Quick start

  1. Fill in System Identification (top).
  2. Drag your scan files onto the Ingest box (or click to browse).
  3. Review and edit rows in the PPSM Register; use filters and bulk-apply for large sets.
  4. Open Endpoints Discovered, load a host inventory if you have one, and name anything still unidentified.
  5. Generate the Boundary Diagram and export it as SVG/PNG for the accreditation package.
  6. Set the Boundary on every row — it drives the diagram and the eMASS export.
  7. Export → eMASS Import (allow.xlsx) for submission, Excel or CSV for your own records; Save Session to keep a working copy.

1 · System Identification

  • System / Enclave Name, Version, Description, POC, Date — apply to the whole register.
  • Network Environment — Unclassified, Classified, or Other (pick Other to type a custom value).
  • System / Enclave Classification — the classification of the system you're documenting (metadata only). It does not change the banner.
  • Document Classification (banner) — the classification of this PPSM document, which drives the colored banner at the top. This is separate on purpose: an UNCLASSIFIED PPSM can document a classified system. You can also click the banner to cycle it.

2 · Ingest scan outputs

Drag & drop or browse — multiple files at once. Auto-detected formats:

  • PDF exports — if a log was printed or pasted into a PDF, the text is pulled back out and run through the normal parsers. Works for a Zeek conn.log, a firewall connection table, a NetFlow cache, anything text-based. It cannot help with a scanned page or an image export, because there is no text in the file to recover; you get told that rather than a silent empty import.
  • Host name sources — a hosts file, a DNS zone file (A/AAAA records), ISC dhcpd.leases or a Windows DHCP CSV, an arp -a table, or an AD / CMDB inventory export (any CSV with an IP column and a name column; OS and owner are picked up too). These files carry no traffic — they teach the tool what each IP is called, and the names are then applied across the whole register.
  • Packet captures — .pcap, .pcapng, .cap. Read as binary right in the browser (classic libpcap little/big-endian and nanosecond, plus pcapng). Ethernet, 802.1Q VLAN, IPv4, IPv6, Raw-IP and Linux SLL are all decoded; packets are aggregated into unique flows with packet and byte counts. Where a TCP handshake is visible, the SYN decides which side is the client — otherwise the better-known port is treated as the service.
  • Firewall connection tables — Cisco ASA / FTD show conn (and show conn all), as raw CLI text or CSV. Interface names are captured into the Source/Destination Zone columns.
  • NetFlow cache — Cisco IOS-XE show flow monitor <name> cache format table, format csv, and the per-record format.
  • Zeek / Bro conn.log (TSV with #fields, or JSON lines).
  • Windows Firewall pfirewall.log (W3C), iptables / UFW kernel logs, ASA/FTD syslog (302013/302015 "Built connection"), tcpdump / tshark text, and pktmon text.
  • nmap XML (-oX), Nessus / ACAS .nessus (including the netstat/connection plugin, which yields outbound flows + remote IPs), Windows netstat -ano, Linux ss (-tulpn for listeners, -tupna to also capture connections) / netstat, and generic CSV.
  • A CSV exported by this tool re-imports cleanly, so you can round-trip a register through Excel.
  • Open ports/listeners become inbound rows (the scanned host is the destination). Active connections become inbound/outbound flow rows with source & destination.

Import options:

  • Include active connections — capture host-to-host flows, not just listeners.
  • Air-gapped — tag imported rows' boundary as “Internal only.”
  • Enclave for this import — stamps each imported row with an enclave name (scan files don't carry one).
  • Collector / source host — the machine the data was gathered from (the NetFlow collector, the firewall, the host you ran the capture on). Scan and capture files don't record this, but PPSM review almost always asks "where did this come from?" — so it is stamped onto every row of the import and travels through the table, filters, exports, and diagram. Set a default under Settings if you always collect from the same box.
  • Listener source port — the source side of an inbound flow is the client's ephemeral port (the OS picks a dynamic port per connection), so it's a range, not one number. This value is written to listeners' Source Port so each row documents the full flow (ephemeral source → fixed service destination) — needed for the registration's Source Port column and for boundary/firewall rules. Default 1024-65535; real ranges vary (Windows 49152-65535, Linux 32768-60999). Only applied to listeners — captured connections keep their actual observed ports.

3 · PPSM Register

  • Every cell is editable. Select rows with the checkboxes (header box selects all filtered); + Add Row adds one; the × removes a row; Dedupe collapses rows that describe the same flow (same source, destination, protocol and port, whichever tool saw it, however the names were capitalised) into the most complete one, and also drops a row already covered by a consolidated row.
  • Source Port / Destination Port — listeners carry the ephemeral range as source and the service port as destination; captured connections show the actual observed ports.
  • Per-row Classification is the marking of the data on that flow (free-text — type compartments/SAP as needed). Different from the System Classification above.
  • Mission Justification is a resizable box for a full engineering rationale.
  • Boundary tags where a flow crosses: Internal only (inside one enclave), Inter-enclave (between enclaves on the same network), Interconnection (to a separately-accredited DCSA system — needs an interconnection agreement), or the DoD numbers B1–B16.
  • Interconnection / Agreement Ref — on Interconnection rows, point to the governing ISA / agreement (e.g. ISA-2026-014).
  • Left-edge highlight: a yellow bar marks a crossing to review (Inter-enclave, Interconnection, or a DISN boundary B1–B8/B15); a teal bar marks Internal only; no bar means no boundary is set yet. (The DISN Vulnerability-Assessment path applies only where a system actually touches the DISN.)

Verifying the tool — Self-Test

The ✓ Self-Test button (top of the page) runs built-in checks of the parsers, exports, and logic right in your browser and reports pass/fail. A green summary means the tool is working on that machine. It runs in isolation and does not touch your loaded data — handy after copying the file to a standalone system.

Working at scale (hundreds–thousands of rows)

  • Search matches across every field by default; use the “in any field” dropdown to scope the search to one column (e.g. only Destination Port). Plus dropdown filters for Enclave, Boundary, and Source tool. Filters combine, and never change your exports — they only change the view.
  • Pagination keeps it fast — only the visible page is rendered.
  • Bulk-apply sets one field across many rows at once. It targets your selected rows when any checkboxes are ticked, otherwise all currently-filtered rows — the label shows which and how many. Pick the field, choose/type the value, Apply; the value control matches the field (dropdown for fixed lists, text for free-form). Clear selection resets it. Examples: filter to 10.20.10 then bulk-set Enclave = ALPHA; or hand-pick a few interconnection rows and set Boundary = Interconnection + Agreement Ref.

Hostnames in the register

Source and Destination each have a separate IP and Hostname column. Keeping them apart matters: PPSM review asks for the system, not just the address, and an address alone is not traceable once DHCP hands it to something else. If you import an older register that combined them as 10.1.1.5 (srv01), the tool splits it automatically on the way in.

The hostname fields autocomplete from every name the tool has learned, so you rarely have to type one twice.

What to run, in order

Each step produces something the next one builds on. Do them in this order and the register largely assembles itself.

  1. Pull existing ACAS / Nessus results — export the .nessus files for the enclave from Tenable.sc. Credentialed scans enumerate listening ports with the netstat plugins (14272 over SSH, 34220 over WMI), which is the least disruptive method and the DoD standard. Produces: most of your listening services, with hostnames and version banners, in one file.
  2. Export your naming source — Get-ADComputer -Filter * -Properties DNSHostName,IPv4Address,OperatingSystem | Export-Csv ad.csv, or the CMDB equivalent. Produces: every address becomes a named system, and you get the owner for the work list.
  3. Fill gaps host-side where ACAS had no credentials — Get-NetTCPConnection -State Listen or netstat -ano on Windows, ss -tulpn on Linux. Produces: the authoritative port-to-process mapping, which is what settles whether a port is really a listener.
  4. Take the firewall connection table — show conn all, or show conn long if your version has it. Produces: what actually crosses the boundary, with interface names that drive the boundary column.
  5. Collect NetFlow from the switches — show flow monitor <name> cache format csv. Produces: east-west flows the firewall never sees, plus ingress interface for boundary determination.
  6. Add passive monitoring if you run Zeek — conn.log. Produces: services on non-standard ports, and conn_state tells refused or unanswered attempts apart from real sessions.
  7. Capture on a host only where nothing else can see the traffic — tcpdump -i eth0 -nn -s0 -w cap.pcap, or pktmon on Windows. Produces: the last few flows, typically same-segment traffic no collector observes.
  8. Run the review checks, fix what they raise, then export. Produces: the eMASS template and the register.

Steps 1 and 2 alone usually get you most of the way. Everything after that is filling gaps and proving boundary crossings.

Assurance categories and where a service goes

Check the CAL before registering. If the service is already listed, register against the existing standard and cite its VA report — duplicating something already on the CAL is the most common reason a submission comes back.

  • Green — best practice, acceptable with minimal mitigation.
  • Yellow — acceptable provided the documented mitigations are in place.
  • Red — banned; will not cross the DISN without an approved exception.
  • Orange — legacy exception; not for new systems.
  • AO / Local Service — internal to the enclave, assessed locally, AO accepts the risk.
  • Temporary — on the CAL pending completion of a VA.

The Submission Path column is derived from the boundary: crossings external to the enclave (B1–B8, B15) go the VA / Further Action route through the PPSM CCB/TAG; internal crossings (B9–B14, B16) go the CLSA route and only your component can register against them. B13/B14 additionally need a DoDIN waiver, which is a separate process from the DSAWG.

PPSM Review Checks

Runs the register against what submissions actually get sent back for, sorted by how much trouble each one causes:

  • Must fix — no boundary set; a destination port in an ephemeral range (32768–60999 or 49152–65535, which nearly always means the capture was read backwards and the client was recorded as the server); no CAL/VA reference; anything marked Red/Banned.
  • Should fix — no data service (the CAL is organised by service, so a bare port cannot be matched); no assurance category; no mission justification; HTTP or HTTPS on a non-standard port, which needs an NSPU exception; B13/B14 without a waiver noted.
  • Worth a look — unnamed internal destinations, and duplicate registrations.

Export Findings writes the whole list to CSV with the offending rows, so it can be worked through away from the tool.

Fill In What Can Be Derived

Most of the register can be worked out from what was collected, so this pass fills it rather than leaving you to type it. By default it only writes into empty cells.

  • Boundary — from the firewall zone names when the data carried them, otherwise from whether each address is inside your ranges. A zone called "outside" is read as "toward the enclave gateway", so a private address behind it becomes B12 rather than B14; only a genuinely public address gets B13/B14. Two internal addresses that your subnet map puts in different enclaves are not internal-use-only either — that traffic crosses the enclave gateway.
  • Enclave — from the subnet map in Settings (10.20.10.0/24 = ALPHA).
  • Hostnames — from the host inventory, applied across every matching row.
  • Submission Path — VA/Further Action or CLSA, from the boundary.
  • Data Service and Data Description — from the destination port and the service table, in plain language ("Directory lookup and authentication" rather than "ldap").
  • Type, Connection Logical Source/Destination Point, VPN flag — the eMASS fields, from the boundary and the address scope.
  • Classification — from the document header. Collector — from the import default.

Mission Justification, CAL status and Assurance Category are deliberately left alone. Those are determinations a person makes and defends, not things to infer from a port number. Assurance will fill only from a service map you supply yourself in Settings.

The pass runs automatically as data comes in. The panel lets you re-run it over all rows or just the filtered ones, choose which fields to touch, and optionally overwrite values that are already there.

Excel workbooks

An .xlsx file is read directly — no need to save it as CSV first. Every sheet is checked, title and filter rows above the table are skipped, and each sheet goes through the same readers a CSV would, so an Excel copy of anything the tool understands is understood too. The import line names the sheet the data came from. Older binary .xls files are not readable; open one in Excel and save it as .xlsx.

NetFlow "top conversations" reports

SolarWinds NTA, ManageEngine NetFlow Analyzer, Plixer, Stealthwatch and similar all export a top-N conversations table, in Excel or CSV. The column names differ between products but the content does not, and all of them are read:

  • Endpoints written as hostname (10.1.1.5), 10.1.1.5 (hostname) or 10.1.1.5:443 are split into address and hostname, and the hostname goes to the host inventory.
  • Where the port is only inside the application label — oracle (1521/TCP) — it is pulled out.
  • Traffic written as 12.4 MB becomes a byte count; protocol numbers 6 and 17 become TCP and UDP.
  • With both ports given, the row is turned round if the report listed the server first.
  • The Total line at the bottom is not treated as a conversation.

Access control policy as a PDF

FMC prints a policy either as a wide table with a row per rule, or as a block of labelled fields per rule. Both are read. A table cannot be read from plain text — a wrapped cell spreads over several lines and interleaves with its neighbours — so the reader works from where each piece of text sits on the page: it finds the header (however many lines it wraps onto), assigns every value to its column by position, and separates the rows by the spacing between them. Tables that align their cells to the top, middle or bottom all read the same, and a policy running across several pages with the header repeated is read as one.

FMC port notation (TCP (6):443, UDP (17):53, HTTPS) is understood. Where the policy names an object instead of an address — WSUS11 rather than 172.22.40.11 — it is resolved against the host inventory once your name sources are loaded. Trust counts as permitting; Monitor does not, because a monitor rule logs traffic and passes it on to the next rule rather than allowing it.

Nessus and ACAS scans

A .nessus file is usually the richest thing you will feed the builder, and everything in it is used:

  • Every name the scan found. FQDN, reverse-DNS name and NetBIOS name. The best becomes the hostname and the rest become aliases, so a lookup by any of them lands on the right host.
  • Operating system and system type, carried into the endpoint list — so a printer or an appliance is recognisable as one.
  • Every interface the host owns. The interface enumeration plugin gives a host's other addresses, and all of them resolve to the same name.
  • The product behind each port, from service detection, into the eMASS Application / Software Record column — Oracle Database 19c Enterprise Edition rather than just oracle_tns. A product named by the scan is kept in preference to one derived from the service name.
  • Whether the service is encrypted, from the SSL and TLS plugins, noted on the row.
  • The host's own connection table, where a credentialed scan collected one through the netstat plugins — giving active connections, not just listeners.
  • Whether the scan ran credentialed. An uncredentialed scan sees only what answered from the network, so its hosts are marked and a review check lists them. Treat those port lists as incomplete.

Tenable and ACAS also export findings as CSV rather than .nessus, and that is read the same way: one row per service, with names taken from the DNS or NetBIOS column.

Firepower / FMC reports

FMC exports a family of reports and they are not interchangeable. The tool works out which one it has been handed from the column names, skipping the title and filter lines FMC puts above the header, and reads each accordingly:

  • Connection events — the richest of the family. Initiator and responder settle direction rather than it being guessed from port numbers, the security zones drive the boundary, and the access control rule ties each flow to the line that permitted it. Blocked connections are recorded as blocked, not as approved services.
  • Servers report — discovered listening services, the closest thing FMC has to a credentialed port enumeration. Vendor and version become the banner. Where traffic to the same service exists, the two are folded into one entry.
  • Network discovery hosts — read as a name source, not as flows. NetBIOS names and operating systems go to the host inventory.
  • Intrusion and security intelligence events — recorded with status Flagged by sensor. A sensor alert is evidence traffic occurred, not evidence it is authorised.
  • Applications report — services with an application name against a port.
  • VPN report — tunnels, flagged as encrypted traffic with the B15 versus B16 decision raised for you, since that turns on whether the far end sits under a different AO.
  • Access control rules — handled by the rules reader described above.

The detected report type appears on the import line, so if it reads something unexpected you will see it rather than having to work it out from the rows.

Hostnames: how every source is cross-referenced

Every file that knows a name feeds one host inventory — DNS zones (forward and reverse), Windows DNS exports, AD and CMDB exports, hosts files, scans, FMC discovery, DHCP leases, NetFlow report labels and ARP tables. That inventory is then applied to every row from every file, in both directions:

  • an address with no hostname gains one;
  • a hostname with no address gains one, and the row's enclave and boundary are then worked out from it;
  • a short name such as WSUS11 is completed to wsus11.range2.mil;
  • a CNAME alias leads to the address it points at.

When sources disagree, the more authoritative one wins, whichever file was loaded first: a reverse-zone PTR record, then forward DNS and AD, then what the host reported about itself, scans, hosts files, FMC discovery, DHCP, NetFlow labels, and ARP last. The losing names are kept as aliases, so looking a host up by any of them still works. A short name shared by two different hosts is never guessed. A host with both an IPv4 and an IPv6 record counts as one host.

For the reverse zones to help, they have to be in the import: the Windows collector exports every zone when run on a DNS server, and the Linux collector copies BIND zone files.

Cross-referencing the sources

No single source has the whole picture. A ruleset knows what is permitted but not who used it. Traffic knows who but not what authorises it. A scan knows the hostnames. Reading them against each other fills the gaps in both directions, and it runs as part of Finish Register:

  • A rule written against a network — permit tcp 172.22.14.0/24 host 172.22.40.11 eq 8530 — gains the host that actually used it, its hostname and its source port, once traffic confirms which one it was.
  • An observed flow gains the rule that permits it, in the Interconnection / Agreement Ref column, so every entry traces back to the line authorising it.
  • Hostnames learned anywhere apply everywhere, whichever source they came from.
  • A rule nobody used keeps its network and no source port. Nothing observed it, so there is nothing honest to put there, and the review checks flag it separately.

Anything derived from an endpoint — enclave, boundary, the eMASS connection points — is recomputed once that endpoint is filled in, so a value worked out from a gap does not survive the gap being closed.

Firewall rules and access control policies

A connection table shows what happened. A ruleset shows what is permitted, which is what PPSM actually registers. Import both and the register can say whether a permitted flow was ever used, and whether an observed flow was ever authorised.

Understood formats:

  • Cisco ASA / FTD access-lists, including object-group resolution. A rule written against groups is expanded into one row per host and port combination, netmasks and IOS wildcard masks become CIDR, and named ports (eq https, eq ntp) resolve to numbers.
  • IOS extended ACLs (ip access-list extended NAME).
  • FMC access control policy exports (CSV with rule name, action, networks and ports).
  • Palo Alto set-format security rules.
  • iptables-save rulesets.
  • Windows Get-NetFirewallRule CSV exports.

Rule rows are marked Permitted by rule or Denied by rule in Status, and the ACL or rule name goes into the Interconnection / Agreement Ref column so an entry can be traced back to the line that authorises it. They never merge with observed traffic, because "this is allowed" and "this happened" are different statements and you want both.

Two review checks appear once both are loaded:

  • Rule permits traffic that was never seen — either the collection missed it, or the rule is stale and should be put forward for removal. Least functionality means the ruleset should not be wider than the traffic needs.
  • Observed traffic with no rule behind it — either a ruleset is missing from your collection, or the traffic is taking a path nobody authorised.

Reading and trimming the register

The table scrolls sideways; the tick box and row number stay pinned to the left so a row can still be identified two thousand pixels along. Addresses, hostnames and the description are wide enough to read in full, and hovering any cell shows its whole value where the text is longer than the column.

Hide addresses, under the filters, leaves rows out of the view. It takes any mix of:

  • an address — 10.20.99.99
  • a network — 172.22.60.0/24
  • a hostname, long or short — scanner99 matches scanner99.range.mil
  • a wildcard — scanner*, *-test

A row is hidden if either end matches, since a scanner or a monitoring host is worth leaving out whichever direction it appears in. The count beside the box says how many are hidden, and the filters below the box still apply to what is left.

Hiding is only a view. Remove hidden deletes those rows from the register for good — useful for stripping a vulnerability scanner or a backup agent out before export. It asks first, and the rows come back if you import the same files again.

Boundaries

Internal traffic gets no B number. Per the PPSM boundary definitions, internal means not crossing any CAL-defined boundary — and that explicitly includes the Enclave Gateway (B11/B12) and the Enclave DMZ (B9/B10). Those flows are tagged Internal, which is a first-class value in the dropdown, not a missing one.

The tool only assigns a number where the addresses prove a crossing:

  • B14 when an address inside your ranges reaches one outside them, B13 for the reverse.
  • Everything else internal-to-internal is Internal.

It never auto-assigns a DISN boundary (B1–B8, B15). Host and firewall output cannot prove that traffic crossed the DISN, and a wrong boundary is worse than a blank one. The full B1–B19 set is in the dropdown for you to set by hand where your architecture warrants it. A review check flags any internal flow that ends up carrying a DISN boundary.

Set Internal ranges under Settings if your enclave uses address space outside RFC1918, or traffic that is really internal will be read as leaving the enclave.

4 · Endpoints Discovered

This is the discovery half of PPSM. Flows tell you which ports are in use; this panel tells you which systems are on the network, what each one is called, and what it serves. Every distinct IP in the register appears once, with:

  • Role — Server (something connects to it), Client (it connects out), or Both. Derived from which side of the flows the endpoint sits on.
  • Services offered — the ports it actually answers on, busiest first. This is the endpoint's PPS footprint in one line.
  • Srv/Cli and Peers — how many flows it serves versus initiates, and how many distinct systems it talks to. A high peer count on a server is normal; a high peer count on a workstation is worth a look.
  • Seen By — which collector observed it, so you know where the evidence came from.

Rows for unidentified endpoints are tinted and carry an input box. Type a hostname straight into it and the name is applied to every matching row in the register at once. The counter at the top tracks how much of the network you have actually identified — the goal is 100%.

  • Load Host Inventory — point it at a hosts file, DNS zone, DHCP lease list, ARP table, or AD/CMDB export. Names are learned and applied immediately.
  • Resolve Hostnames — re-applies the inventory after you have imported more flow data.
  • Unidentified Work List — exports just the endpoints with no name, with blank Hostname and Owner columns to fill in. Send it to whoever owns the network, then load the completed file back in with Load Host Inventory. That round-trip is the fastest way to close out discovery.
  • Export Endpoints — the full inventory: IP, hostname, role, services, flow counts, peers, enclave, boundaries, OS, owner, and collector.

Names are learned automatically from nmap and Nessus scans too, since those carry hostnames and FQDNs. Anything learned is remembered for the session and saved inside Save Session.

5 · Boundary Diagram

Generates a diagram straight from whatever is in the register, so the picture and the data can't drift apart. Two types:

  • Environment diagram (default) — the topology of your environment rather than a template. It draws only the PPSM connection points your register actually uses, labels the enclave nodes with your enclave names, and draws one arrow per boundary crossing found in the data, weighted by flow count and annotated with the ports crossing it. Crossings that are AO responsibility, need a DoDIN waiver, or are tunnels get called out. Rows whose boundary isn't set yet appear in a "not yet mapped" strip, so gaps show up instead of quietly vanishing.
  • Flow map — built from your rows. Sources on the left, boundaries/destinations on the right, one curve per group. Line weight scales with flow count, the bubble shows the count, and each boundary node lists its busiest ports. Group by Enclave → Boundary, Source zone → Dest zone (useful for firewall interface data from show conn), or Collector → Boundary.
  • DoD 16-boundary reference — the standard PPSM boundary topology (enclaves, gateways, DMZs, DISN, external networks) with every boundary that has traffic in your register highlighted and labelled with its count. Boundaries with no data stay greyed out, which makes coverage gaps obvious at a glance. Non-DISN tags (Internal only, Inter-enclave, Interconnection) are summarised along the bottom.
  • Data scope — diagram all rows, or only the rows currently passing your filters. Filter to one enclave and generate a per-enclave diagram.
  • Theme — Dark, Light, or Print (black & white, for pasting into a document).
  • Export — SVG (vector, scales cleanly in Word/PowerPoint), PNG at 1–4× scale, or Print/PDF.
  • Yellow = a crossing worth reviewing; teal = internal only. Same colour logic as the register's left-edge bars.

eMASS export

eMASS Import (allow.xlsx) is the PPSM Boundary Information Import Template itself, filled in and ready to submit. It reproduces the template one for one: the CUI banner and system header block across rows 1–7, the 21 columns A–U in the template's order on row 8, and the Glossary and Instructions sheets beside the PPSM sheet. Boundary, Direction, the two Connection Logical Point columns, Type, VPN Tunnel Type and VPN / Encrypted Tunnel Traffic all keep the template's dropdowns, pointed at the Glossary. The dropdowns are wired through named ranges, so they render in every version of Excel — click a Boundary, Direction, Type, Connection Logical Point, VPN Tunnel Type or VPN / Encrypted Tunnel Traffic cell and choose from the list rather than typing. The # column is left blank because eMASS generates it on import, and every field is filled from the register where the data allows — Purpose included: a row with no Mission Justification gets a statement generated from the service and the two ends (Settings › eMASS template turns that off, and sets VPN / Encrypted Tunnel Traffic, VPN Tunnel Type and the physical location of each end for the whole export); on export the tool names any required field still empty. Nothing is renamed, reordered or added, so the file imports as the template.

Four fields cannot be derived from collected traffic and must be set by you: Type, Connection Logical Source Point, Connection Logical Destination Point, and the VPN / Encrypted Tunnel Traffic flag. Those columns are hidden in the table by default — unhide them under Settings, or fill them in Excel afterwards using the Glossary dropdowns. The export reports how many rows are still incomplete.

Don't add, remove or reorder columns in the exported file, and don't delete the classification label or the Glossary sheet; eMASS rejects a template whose shape has changed.

Settings & customization

  • Well-known port ceiling — when nothing in the data says which side opened a connection, the endpoint with the lower/better-known port is treated as the server. Raise or lower this if your environment puts services on high ports.
  • Packet capture options — minimum packets per flow (the fastest way to strip scan noise from a big capture), a maximum packet budget to keep the browser responsive, and toggles for ICMP, non-TCP/UDP protocols, and broadcast/multicast.
  • Subnet to enclave map — 10.20.10.0/24 = ALPHA, one per line. Fills the Enclave column, and lets the tool tell cross-enclave traffic apart from internal-use-only traffic.
  • Custom service names — 9997 = splunk-forwarder or TCP/8443 = vendor-mgmt-gui, one per line. These override the built-in port table everywhere, so your program's own applications get named instead of showing a bare port.
  • Custom boundary tags — add your own alongside Internal only / Inter-enclave / Interconnection / B1–B16 (e.g. a cross-domain solution or a vendor maintenance path).
  • Visible columns — hide columns you don't use; hidden columns drop out of CSV and Excel exports too.
  • Import defaults — default enclave and collector, pre-filled on every import.
  • Save / Load Profile (Export section) — saves just the settings, no data. Hand the profile to the rest of the team so everyone's registers come out consistent. Settings also ride along inside a saved session.

4 · Export

  • Excel (.xlsx) — formatted workbook, frozen header, autofilter, dropdowns, highlighted crossings. Built fully offline (no libraries).
  • CSV — imports into any spreadsheet / registration template.
  • Printable Report — opens a print-ready page (Ctrl/Cmd-P → Save as PDF). If popups are blocked it downloads as HTML instead.

Running it

It's one HTML file — no install, no server. Windows: double-click (opens in Edge) or right-click → Open with a browser. Linux: double-click, xdg-open, or open in Firefox/Chromium. Works on either OS.

Flow orientation
When a capture doesn't show which side opened the connection, the endpoint with the lower / better-known port is treated as the server. Windows ephemeral is 49152-65535; Linux 32768-60999.
Packet capture (pcap / pcapng)
Raising the minimum-packets threshold is the quickest way to strip scan noise out of a large capture. Reading stops at the max-packet limit to keep the browser responsive.

Scope. This tool assembles a PPSM register (DoDI 8551.01 data model). It does not certify compliance — accuracy of inputs and the boundary / assurance analysis remain the assessor's responsibility.
Boundary tagging. Traffic that never crosses a CAL-defined boundary is tagged Internal and carries no B number — internal means not crossing the Enclave Gateway (B11/B12) or the Enclave DMZ (B9/B10) either. The tool only assigns a number where the addresses prove a crossing: B13/B14 when one end is outside your ranges. It never auto-assigns a DISN boundary (B1–B8, B15), because host and firewall data cannot prove a DISN crossing — set those yourself where your architecture warrants it, and confirm them with your AO / ISSM.
Collector. Every row records the host the data was gathered from, so an entry can always be traced back to the sensor, firewall, or workstation that observed it.
Endpoints. An address is not a system. Every endpoint should end up with a hostname before the register goes forward — the identification counter shows how far along you are.
Diagram. The boundary diagram is generated from the register itself — regenerate it after edits so the picture and the data stay in step. It supports the analysis; it is not a substitute for your approved network architecture drawing.
Privacy. All parsing happens in your browser — including packet captures, which are decoded locally and never leave the machine. Nothing is uploaded. Safe for standalone / air-gapped use — save the file locally and open with any browser.
