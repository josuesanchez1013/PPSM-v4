PPSM BUILDER
============

A PPSM register has to say, for every service an enclave uses: what protocol
and port, on which system, crossing which boundary, permitted by what, and
why it needs to exist. That data is scattered across hosts, firewalls,
switches, scanners and DNS, in a dozen formats that do not agree with each
other.

This package collects it, cross-references it, and turns it into the eMASS
PPSM template.

Everything runs locally in a browser. Nothing is uploaded, nothing is
installed, there is no network call of any kind. It works on a standalone or
air-gapped workstation, and so do the collector scripts.


SUPPORTED PLATFORMS

  Collection
    RHEL 8 and RHEL 9        as shipped. Uses ss from iproute2 and ip from
                             the same package, both present by default.
                             net-tools (arp, netstat) is NOT installed on
                             either, so nothing depends on it.
    Windows 10 and 11        PowerShell 5.1, which both ship with, or
                             PowerShell 7. No modules needed for host
                             collection; RSAT adds the AD export and
                             DnsServer adds the DNS zones.
                             ppsm-collect.ps1 checks $PSVersionTable on
                             every host. Where Get-NetTCPConnection is
                             missing (older builds, locked-down images,
                             PowerShell 2.0/3.0 without NetTCPIP) it reads
                             netstat -ano instead and says so; the shell
                             version and method used are written to the
                             Collector column of each connections CSV and
                             to READ-ME.txt.
                             Hosts are collected in parallel (-ThrottleLimit,
                             32 at once by default). Every host's WinRM port
                             is probed at the same time first; one that does
                             not answer within -ProbeTimeout seconds (5) is
                             skipped and listed as unreachable, and a host
                             that answers but stalls is dropped after
                             -ConnectTimeout / -HostTimeout. The run never
                             waits on one host.
                             Run  .\ppsm-collect.ps1 -SelfTest  once on a
                             5.1 host: it collects the machine both ways,
                             compares the listener lists and writes
                             ppsm-selftest\SELFTEST.txt with a PASS/CHECK
                             verdict and both CSVs to drop on the builder.
    ppsm-collect.py          Python 3.6 and later, so it runs on RHEL 8 as
                             shipped. On a minimal RHEL 8 without
                             /usr/bin/python3, run it as
                             /usr/libexec/platform-python ppsm-collect.py
    ppsm-collect.sh          bash 4.4+ (RHEL 8) and 5.x (RHEL 9). POSIX
                             tools only; no grep -P, no net-tools.

  The builder
    Any current browser, opened from a local file. Chrome, Edge and Firefox
    on Windows 10/11, and Firefox or Chromium on RHEL 8/9.

  Encodings
    PowerShell 5.1 writes UTF-8 with a BOM from Export-Csv, and UTF-16 from
    a plain redirect. Both are read correctly; nothing needs converting.

THE WHOLE JOB
-------------

Two ways to collect. Both produce the same ppsm-results folder and the tool
reads it the same way. Use SCRIPTED unless scripts are not permitted on the
system, in which case MANUAL gives every command to run by hand.

The SOP has both as tick-off cards with Done and N/A against each step, and
each path keeps its own ticks. What follows is the same thing in brief.

Every step is tagged with the box you run it on:

  [WINDOWS HOST]       PowerShell, Run as Administrator
  [LINUX HOST]         a shell, with sudo
  [DOMAIN CONTROLLER]  any machine with the RSAT / DnsServer modules
  [FIREWALL]           FMC -> Devices -> Device Management -> Threat Defense
                       CLI, or SSH to the management address
  [SWITCH]             SSH to the switch management address
  [FMC CONSOLE]        the FMC web console, in a browser
  [ANSIBLE NODE]       wherever ansible-playbook runs
  [YOUR WORKSTATION]   your own desktop

Run host commands elevated. Without Administrator or sudo the process behind
each port is missing, and that is the field that proves a port is a real
listening service rather than a passing connection.


SCRIPTED - 10 steps
-------------------

  A. WINDOWS HOSTS            (skip the group if the enclave has none)
     1. [WINDOWS HOST] one domain-joined machine
          cd C:\ppsm
          .\ppsm-collect.ps1
        ...to reach the other Windows hosts in the same run:
          .\ppsm-collect.ps1 -ComputerListFile hosts.txt

     2. [DOMAIN CONTROLLER] run the collector once on a DC
          cd C:\ppsm
          .\ppsm-collect.ps1
        A DC normally has both the ActiveDirectory and DnsServer modules, so
        this one run exports every computer account AND every DNS zone,
        forward and reverse. Check that inventory\ad-computers.csv and
        inventory\dns-records.csv both came out.

  B. LINUX HOSTS              (skip the group if the enclave has none)
     3. [LINUX HOST] one host
          cd /opt/ppsm
          sudo ./ppsm-collect.sh
        ...to reach the others over SSH in the same run:
          sudo ./ppsm-collect.sh -H hosts.txt -u svc-ppsm

     4. [ANSIBLE NODE] or the whole fleet at once
          ansible-playbook -i inventory.ini ppsm-collect.yml
        Replaces steps 1, 3, 5 and 6 if your inventory covers everything.

  C. NETWORK DEVICES          (the boundary evidence)
     5. [FIREWALL] the connection table
          terminal pager 0
          show conn all
          -> ppsm-results\network\firewall-showconn.txt

    5b. [FIREWALL] the ruleset, in the same session
          show running-config access-list
          show running-config object-group
          -> ppsm-results\network\firewall-acl.txt
        Take the object-groups as well, or a rule written against a group
        cannot be expanded into the hosts and ports it covers.

    5c. [FMC CONSOLE] the FMC reports, if the firewall is managed by FMC
          Connection Events     Analysis -> Connections -> Events
          Servers               Analysis -> Hosts -> Servers
          Hosts                 Analysis -> Hosts -> Network Map
          Access control policy Policies -> Access Control -> report icon
          Site-to-site VPN      Devices -> VPN -> Site To Site
        Export to CSV where you can; the policy report is also read as PDF.

     6. [SWITCH] the NetFlow cache, per switch
          show flow monitor ?
          show flow monitor <name> cache format csv
          -> ppsm-results\network\<switch>-netflow.csv
        Nothing listed after the ? means NetFlow is not configured there.
        Or, if you run a NetFlow analyser (SolarWinds NTA, ManageEngine,
        Plixer, Stealthwatch), export its Top Conversations report for the
        last 30 days as .xlsx instead - it covers every switch at once.

  D. FINISH IN THE TOOL
     7. [YOUR WORKSTATION] export the ACAS scan as .nessus into
        ppsm-results\ if the enclave is scanned, then drag the whole folder
        onto the ingest box.
     8. [YOUR WORKSTATION] Export -> eMASS Import (allow.xlsx), then Save
        Session before closing the tab.


MANUAL - 14 steps
-----------------

  SETUP
     1. [YOUR WORKSTATION] create the folders
          ppsm-results\hosts\  inventory\  network\

  A. WINDOWS HOSTS            (repeat per host; skip if none)
     2. [WINDOWS HOST] ports and connections
          Get-NetTCPConnection |
            Select-Object *,@{n='Process';e={(Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue).ProcessName}} |
            Export-Csv -NoTypeInformation "$env:COMPUTERNAME-tcp.csv"

          Get-NetUDPEndpoint |
            Select-Object *,@{n='Process';e={(Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue).ProcessName}} |
            Export-Csv -NoTypeInformation "$env:COMPUTERNAME-udp.csv"
          -> ppsm-results\hosts\

          If Get-NetTCPConnection is "not recognized" on that host (check
          with $PSVersionTable.PSVersion), use netstat instead — the
          builder reads it as long as the file name carries the host:
          netstat -ano > "$env:COMPUTERNAME-netstat.txt"

        Name the files after the host. That name is how a service listening
        on 0.0.0.0 gets attributed to the right machine.

        Simpler, if process names are not needed:
          netstat -ano > %COMPUTERNAME%-netstat.txt
        covers TCP and UDP in one command and is read just as well.
        Elevated, netstat -anob adds the executable name.

     3. [DOMAIN CONTROLLER] computer names (run once, not per host)
          Get-ADComputer -Filter * -Properties DNSHostName,IPv4Address,OperatingSystem |
            Where-Object IPv4Address |
            Select-Object Name,DNSHostName,IPv4Address,OperatingSystem |
            Export-Csv -NoTypeInformation ad-computers.csv
          -> ppsm-results\inventory\

    3b. [DOMAIN CONTROLLER] the DNS zones, forward AND reverse
          Get-DnsServerZone | Where-Object { -not $_.IsAutoCreated } | ForEach-Object {
            $z = $_.ZoneName
            Get-DnsServerResourceRecord -ZoneName $z |
              Where-Object RecordType -in 'A','PTR','CNAME' |
              Select-Object HostName, RecordType, @{n='ZoneName';e={$z}},
                @{n='IPv4Address';e={$_.RecordData.IPv4Address.IPAddressToString}},
                @{n='PtrDomainName';e={$_.RecordData.PtrDomainName}},
                @{n='HostNameAlias';e={$_.RecordData.HostNameAlias}}
          } | Export-Csv -NoTypeInformation dns-records.csv
          -> ppsm-results\inventory\

        The record data has to be expanded like that. A plain Export-Csv
        writes "DnsServerResourceRecordA" where the address should be, which
        is no use. Where PowerShell is not available,
        dnscmd /zoneprint <zone> > zone.txt is read just as well.

     4. [WINDOWS HOST] the local hosts file
          copy %SystemRoot%\System32\drivers\etc\hosts hosts-file.txt
          -> ppsm-results\inventory\

  B. LINUX HOSTS              (repeat per host; skip if none)
     5. [LINUX HOST] ports and connections
          H=$(hostname -s)
          { echo "# ppsm-host: $H"; sudo ss -tuanp; } > $H-sockets.txt
          -> ppsm-results/hosts/

        One pass covers listeners, active connections and the process behind
        each socket.

        The ppsm-host line is not optional. A service listening on 0.0.0.0
        does not say which machine it is on, and that line is how the tool
        attributes it.

     6. [LINUX HOST] the local name sources
          cp /etc/hosts hosts-file.txt
          ip neigh > arp-table.txt
          -> ppsm-results/inventory/

    6b. [LINUX HOST] the BIND zone files, if DNS runs on BIND
          sudo cp /var/named/*.zone /var/named/*.rev ppsm-results/inventory/
          sudo cp /etc/bind/db.* ppsm-results/inventory/
        Take the reverse zones as well. Leave out the stock files -
        db.local, db.127, db.root - they name nothing in your enclave.

  C. NETWORK DEVICES
     7.  [FIREWALL] connection table   (as scripted step 5)
    7b.  [FIREWALL] ruleset            (as scripted step 5b)
    7c.  [FMC CONSOLE] FMC reports     (as scripted step 5c)
     8.  [SWITCH] NetFlow              (as scripted step 6)

  D. FINISH IN THE TOOL
     9.  [YOUR WORKSTATION] add the ACAS scan, then import the folder
    10.  [YOUR WORKSTATION] export the eMASS template, save the session

If you are short on time: group A or B, plus the firewall connection table.
Everything else improves the result rather than making it possible.


WHICH ADDRESS ENDS UP WHERE

Every source writes the two ends of a flow differently, and PPSM registers
the LISTENING SERVICE, never the client. One rule covers all of it: the end
offering the service becomes the Destination, and whoever reached it becomes
the Source.

  Source                    Destination IP comes from      Source IP
  ------------------------  -----------------------------  ------------------
  ss / netstat              Local Address on a LISTEN line the peer on ESTAB
  Get-NetTCPConnection      LocalAddress when State=Listen the other end
  Get-NetUDPEndpoint        LocalAddress                   (none)
  show conn (ASA/FTD)       the end with the known port    the other end
  FMC connection events     Responder IP                   Initiator IP
  FMC servers report        IP Address                     (none)
  NetFlow cache             IPV4 DST ADDR                  IPV4 SRC ADDR
  Top conversations         the endpoint with the service  the other endpoint
  Zeek conn.log             id.resp_h                      id.orig_h
  Windows Firewall log      the end with the known port    the other end
  ASA syslog                the end with the known port    the other end
  pcap / tcpdump            the end with the known port    the other end
  nmap / Nessus             the scanned host               (none)
  access-list / policy      destination network            source network
  DNS forward zone          name -> address (fills names on existing rows)
  DNS reverse zone          address -> name (the owner, read backwards)

ADDRESSES THAT POINT NOWHERE

  0.0.0.0, *          every interface on this host. Attributed to the machine
                      the file came from - which is why the collector writes
                      a "# ppsm-host:" line, and why a Windows CSV should be
                      named after its host.
  127.0.0.1,          loopback. A service bound only to loopback cannot leave
  127.0.0.53          the host, so it crosses no boundary and is not
                      registrable. Skipped, with the count on the import line.
  any IPv6 address    set aside on import, with the count shown. The register
                      is IPv4 only by default, so a stray AAAA record or a
                      link-local flow never reaches it. Turn that off under
                      Settings if the enclave really does run dual stack.
  an ephemeral port   32768-60999 or 49152-65535 as the DESTINATION nearly
  as the destination  always means the capture was read backwards. The review
                      checks flag these rather than registering a client.
  a MAC address       not an endpoint, and never treated as one.
  172.22.14.0/24      a network stays a network: a valid rule source, but it
                      never gains a hostname.


EVERY FILE THE BUILDER READS
----------------------------

REQUIRED - the register cannot be built without these

  Host ports and connections   Windows: <host>-connections.csv or -netstat.txt
                               Linux:   <host>-sockets.txt
                               Every listening service and connection, with
                               the process behind each port.
  Firewall connection table    network\firewall-showconn.txt, or FMC
                               Connection Events. What actually crosses the
                               boundary, with the interface names that set
                               the Boundary column.
  At least one name source     AD export and/or DNS zones. Without one the
                               register is a list of bare addresses.

STRONGLY RECOMMENDED - each closes gaps the required files leave

  DNS zones, forward+reverse   inventory\dns-records.csv, zone-*.zone/*.rev
                               The authoritative hostname for every address.
  Firewall ruleset             network\firewall-acl.txt, or the FMC policy
                               report (PDF or CSV). What is permitted.
  ACAS / Nessus scan           *.nessus. Credentialed listening services with
                               version banners.
  NetFlow                      switch cache CSV, or an analyser's Top
                               Conversations report (.xlsx). East-west flows
                               the firewall never sees.
  FMC Servers and Hosts        Discovered services, and hostnames and
                               operating systems nothing else knows.

WHEN YOU HAVE THEM - situational, read automatically if dropped in

  FMC intrusion / security intelligence events    flagged traffic
  FMC site-to-site VPN report                     tunnels, B15/B16 decision
  Zeek conn.log                                   non-standard ports
  pcap / pcapng, tcpdump text, pktmon             flows nothing else sees
  pfirewall.log, Get-NetFirewallRule export       host-level allow/deny
  ASA syslog, iptables-save, Palo Alto config     more flows and rules
  nmap XML (-oX)                                  services from the network
  hosts files, DHCP leases, neighbour tables, CMDB extra names
  the filled-in work list                         the last few names

FORMATS

  Anything above can arrive as CSV, as an Excel .xlsx workbook, or as a
  text-based PDF. Each file is identified from its contents, not its name,
  and the import line says what it was taken to be.

  Not readable: older binary .xls (save as .xlsx), scanned or image-only
  PDFs, and zip archives (extract them first). Read-me and notes files in
  the folder are skipped rather than reported as errors.


FILLING SOURCE FROM ACAS (AND WHAT ELSE TO PROVIDE)

An ACAS / Nessus scan finds LISTENING SERVICES. That is the destination side
of a flow - the host, its port, the product. A scan cannot see who connects
TO those services, so on its own it leaves the Source columns blank.

To fill the source, add anything that shows conversations for the same hosts
and ports. The tool matches them to the scanned services automatically:

    firewall connection table   show conn all           best - real client IPs
    firewall ruleset            show running-config      who is PERMITTED to
                                access-list + object-group   reach each service
    NetFlow cache               show flow monitor ...    client IPs and volume
    Zeek conn.log               conn.log                 client IPs, non-std
                                                         ports

Order of value: the firewall connection table gives actual source addresses;
the ruleset gives the authorised sources even for services not seen live;
NetFlow and Zeek fill the rest. With ACAS plus the firewall connection table,
nearly every row gets a source.

The review checks flag any row where a scan found the service but nothing
provides the source, and name the file types that would close the gap. So the
minimum useful set of documents is:

    1. the ACAS / Nessus scan          (destination, service, product, OS)
    2. the firewall connection table   (source addresses)
    3. a name source - AD export or    (turns addresses into hostnames on
       DNS zones                        both ends)

Those three fill most of the register between them.


APPLICATION NAMES TO SERVICE NAMES

A scan reports a product in the Application/Software Record Name - "Microsoft
SQL Server 2019", "Apache/2.4.57", "OpenSSH_8.7". PPSM wants the common
service in Data Service. The builder maps one to the other from a broad
directory covering web and app servers, databases, directory/auth, mail,
remote access, management and monitoring, virtualisation and containers, data
stores and brokers, VoIP, file/print, backup, and security tooling - plus the
enterprise and DoD products common on government networks.

When a row has a product name but no Data Service, it is filled from the
product; where the row also has no port, the product's usual port is supplied.
An existing Data Service is never overwritten. Version numbers and punctuation
are ignored, so "Apache/2.4.57 (Unix)" and "Apache httpd 2.4" both resolve to
the same service.

Data Service carries the service's NAME, not a code or a bare acronym:
"Remote Desktop Protocol (RDP)" rather than ms-wbt-server, "Lightweight
Directory Access Protocol (LDAP)" rather than ldap, "Server Message Block
(SMB)" rather than microsoft-ds or cifs. Codes that arrive from a scan
(www, cifs, epmap), from Zeek (ssl) or from a CSV are upgraded when the
register is finished. A name you type yourself is left exactly as typed.
A Windows process name (svchost, wsusservice) is an application, so it goes
to Application/Software Record Name and the service is named from the
product directory or the port.


EXCLUDING EPHEMERAL PORTS

Two options under Settings, below the ephemeral range:

  Clear ephemeral source ports   On by default. A client's high source port
                                 (in the ephemeral range) is never the service,
                                 so it is cleared from the Source column rather
                                 than cluttering the register.
  Exclude ephemeral destination  Off by default. Drops observed rows whose
                                 DESTINATION port is in the ephemeral range -
                                 these almost always mean the capture was read
                                 backwards. Firewall-rule rows and rows already
                                 Registered in eMASS are always kept.

The range itself is the "Ephemeral / listener source range" field; set it to
match your OS (Windows 49152-65535, Linux 32768-60999) or your own policy.


DNS EXPORTS AS CSV

Besides Windows Get-DnsServerResourceRecord output and BIND zone files, the
builder reads a DNS export - as a .csv OR a plain .txt file - with columns
like:

    name (hostname), type, data (IP), timestamp

It is detected by its content, not just its header, so almost any real-world
shape works: comma, tab, pipe, or space-delimited; with a header row or none
at all; columns in any order; extra columns (class, TTL, aging); a leading
BOM; and quoted fields. Windows "HostName,RecordType,...,RecordData" exports,
"name/type/data/timestamp" dumps, and bare "host A 10.0.0.5" lists are all
read. Verbose record-type labels are understood too - "A Record", "Host (A)",
"Pointer (PTR)", "Alias (CNAME)" as well as the bare A / PTR / CNAME - and the
delimiter can be comma, semicolon, tab, pipe or spaces. Flow data, netstat, and zone files are left to their own parsers.

As a final catch-all, ANY CSV or text table that has a column of hostnames and
a column of IP addresses - whatever the headers, column order, or record-type
wording, even with no type column at all - is read as a name/IP list and used
to resolve hostnames. So if a DNS or inventory export is not recognised as one
of the specific formats above, its names are still learned as long as it pairs
hostnames with addresses. The import log shows "name/IP list - N names learned". Each record is used to match hostnames to IPs:

    A / AAAA    hostname <-> address, filled into every row either way
    CNAME       recorded as an alias, so a row using the alias still resolves
    PTR         address -> hostname, with the arpa name in either column

Drop it in with the rest of the collection. Any row that has only an IP gains
its hostname, any row that has only a hostname gains its IP, and short names
are completed - the same resolution every name source feeds.


A REGISTER THAT HAS HOSTNAMES INSTEAD OF ADDRESSES

Often the PPSM you start from names the systems and never gives their
addresses: an eMASS export with the FQDN columns filled and the IP columns
empty, or a register someone kept by hand with "wsus11" in the Source IP
column. The template needs both. Drop the register in with a DNS export and
the tool fills the addresses in from the names:

    the register        any CSV / Excel in the template's column layout, or
                        with Source / Destination / Protocol / Port columns.
                        Hostnames may sit in the IP columns or the FQDN
                        columns, several per cell joined by semicolons.
    the DNS export      DNS Manager's right-click export, dnscmd /enumrecords
                        or /zoneprint, Get-DnsServerResourceRecord as CSV, a
                        BIND zone file, or any name/type/address table - as
                        .csv, .txt, .tsv or .xlsx. Forward AND reverse zones
                        if you have them.

Short names in the export are completed with the zone. If the export has no
zone column the zone is worked out from the SOA row it usually carries, from
the file name when it is the zone ("range2.mil.csv"), from the suffix most
rows share, or from the DNS domain under Settings - set that if the import
line does not say "short names qualified under <zone>".

After import, Resolve Hostnames reports what happened:

    N addresses found from a name     filled in from the zones
    N short names completed           WSUS11 -> wsus11.range2.mil
    N name/address mismatches         the row names the system one way and
                                      DNS names that address another way.
                                      The row is left alone and annotated;
                                      the review check lists them.
    N hostnames still without an      no zone, hosts file or inventory knows
    address                           them. They are listed under Endpoints
                                      Discovered with a box to type the
                                      address into, and go out on the
                                      Unidentified Work List.

Nothing is guessed: a name two hosts share is never resolved, and a name no
source knows stays blank and is raised as a must-fix check rather than
filled with a lookalike.


NESSUS AND ACAS SCANS

A .nessus file is usually the richest thing you can feed the builder, and
everything in it is used:

    names            FQDN, reverse DNS and NetBIOS. The best becomes the
                     hostname, the rest become aliases, so a lookup by any
                     of them lands on the right host.
    OS and type      carried into the endpoint list, so a printer or an
                     appliance is recognisable as one.
    interfaces       the interface enumeration plugin gives a host's other
                     addresses; all of them resolve to the same name.
    the product      service detection fills the eMASS Application /
                     Software Record column - "Oracle Database 19c
                     Enterprise Edition", not just "oracle_tns". A product
                     named by the scan beats one derived from the service.
    encryption       the SSL/TLS plugins mark the service as encrypted.
    connections      where a credentialed scan collected the host's netstat
                     output, that gives active connections, not just
                     listeners.
    credentialed?    an uncredentialed scan sees only what answered from the
                     network. Those hosts are marked and a review check
                     lists them; treat their port lists as incomplete.

Tenable and ACAS also export findings as CSV rather than .nessus. That is
read the same way: one row per service, with names from the DNS or NetBIOS
column.


HOW THE SOURCES FILL EACH OTHER'S GAPS
--------------------------------------

No single source has the whole picture. Dropping the folder in runs all of
this automatically.

NAMES. Every name source feeds one inventory, applied to every row from
every file, in both directions:

  an address with no hostname      gains one
  a hostname with no address       gains one, and the row's enclave and
                                   boundary are then worked out from it
  a short name like WSUS11         completed to wsus11.range2.mil
  a CNAME alias                    leads to the address it points at

Where sources disagree, the most authoritative wins whichever file loaded
first: reverse DNS, then forward DNS and AD, then the host itself, scans,
hosts files, FMC discovery, DHCP, NetFlow labels, and ARP last. The losing
names are kept as aliases, so a lookup by any of them still lands on the
right host. A short name shared by two different hosts is never guessed. 

RULES AGAINST TRAFFIC. A rule written against a network gains the host that
actually used it, its hostname and its source port. An observed flow gains
the rule that permits it. A rule nobody used keeps its network and no source
port - nothing observed it, so there is nothing honest to put there - and it
is reported separately instead.

SERVICES AND FLOWS. A listening service found by a scan or the FMC servers
report folds into the traffic that used it, so one row carries both the
version banner and the client.

REPEAT SIGHTINGS. The same flow usually appears in several sources. Those
merge into one row as they import, and the Source Tool column lists every
tool that saw it, for example "show-conn, netflow, zeek". Where two sources
disagree, firewall interface names beat an address-only guess, so the result
does not depend on which file loaded first.


ACAS SOFTWARE INVENTORY
-----------------------

A credentialed scan lists what is installed on each host. The builder
reads that from the .nessus file or a Tenable CSV findings export -
Windows "Installed Software Enumeration" (plugin 20811), "Software
Enumeration (SSH)" for RPM/DEB packages (22869), the CPE list (45590) and
the Windows service list (44401) - and keeps it per address. The Endpoints
table shows a Software count per host; hover it for the list.

It is joined to the register during Fill In (and the automatic pass on
import): where a row's Application/Software Record Name is blank, a bare
process name (svchost, sqlservr, w3wp) or just a copy of the service, the
installed product that serves that port is written instead - "Microsoft
SQL Server 2019 (64-bit) 15.0.2000.5" behind 1433, "Splunk Universal
Forwarder 9.1.2" behind 8089. A product is matched by the port it usually
serves, by the service it implies, or by the process it is known to run
as. A proper product name already in the row is never replaced.

Where the host has an inventory and nothing in it accounts for the port,
the row is noted ("no matching software in the ACAS inventory for this
port") and the review checks list it under "worth a look" - that is a
listener to name by hand. Hosts the scan did not inventory are not
touched. The inventory is saved with the session.


BOUNDARIES
----------

Internal traffic gets no B number. Internal means not crossing any
CAL-defined boundary, and that explicitly includes the Enclave Gateway
(B11/B12) and the Enclave DMZ (B9/B10). Traffic that stays inside is tagged
"Internal" - a real value, not a gap. Do not go looking for a B number to
put there.

What gets derived:

    both ends inside your ranges     Internal - no B number, no CAL lookup,
                                     no submission
    inside -> outside your ranges    B14
    outside -> inside                B13
    anything it cannot tell          left blank for you

The tool never assigns a DISN boundary (B1-B8, B15) on its own. Nothing in
host output, a firewall connection table or a flow cache can prove a flow
crossed the DISN. Those are yours to set where the architecture warrants it,
and to confirm with your AO or ISSM. A review check flags any internal flow
that has ended up carrying a DISN boundary.

If your enclave uses address space outside RFC1918, set Internal ranges
under Settings before importing. Without it, traffic that is really internal
reads as leaving the enclave and picks up a B14 it does not deserve.


WHAT IS LEFT FOR YOU
--------------------

Three fields are judgements rather than observations, so no tool can fill
them. Internal rows need none of them.

  Mission Justification   the system or application owner. Why the flow
                          needs to exist. A reviewer reads this first.
  CAL / VA Reference      the PPSM CAL. Look the service up before
                          registering; if it is already listed, cite its VA
                          report rather than raising a duplicate.
  Assurance Category      the CAL entry for that service, or your own CLSA
                          for a local one.

Fill them in the table, or select several rows and use Bulk apply.

Assurance categories, for the rows that do cross a boundary:

    Green         Best practice. Acceptable with minimal mitigation.
    Yellow        Conditional. Acceptable with documented mitigations.
    Red           Banned. Will not cross the DISN without an exception.
    Orange        Legacy exception. Not for new systems.
    AO            Local Service. Internal to the enclave, AO accepts risk.
    Temporary     On the CAL pending completion of a VA.

Submission path, derived from the boundary:

    B1-B8, B15    VA / Further Action, through the PPSM CCB/TAG
    B9-B14, B16   CLSA, component local
    B13, B14      additionally require a DoDIN waiver
    Internal      no submission

Register the listener, never the client. A destination port in 32768-60999
or 49152-65535 almost always means the capture was read backwards.


CONSOLIDATING LIKE ENDPOINTS

When the same source reaches the same destination on several ports, those
collapse into ONE row with the ports joined by semicolons - the format the
eMASS template accepts. A workstation subnet reaching a domain controller on
88, 389 and 636 is one registration reading "88; 389; 636", not three rows.
Data Service, the application name and the counts are joined the same way and
kept aligned to their ports.

It leaves alone what should stay separate: a different source, a different
destination, a different protocol, boundary or direction each keep their own
row. On the sample set this takes the register from 76 rows to 55.

Sources are consolidated the same way: when several source IPs reach the
same destination on the same port and service, they become one row with the
source IPs joined by semicolons. Between the two passes the sample register
goes from 76 rows to 29.

It also runs automatically at export time, so the eMASS file is always
consolidated even if you did not press Finish Register first. On by default;
the toggle is under Settings, and "Consolidate ports" beside Dedupe runs it
on demand.


READING AN eMASS EXPORT BACK IN

eMASS can export the registered PPSM entries - as a CSV, or an .xlsx with a
"PPSM Info" tab carrying port, protocol, service and host/IP. Drop that in
and the tool reads it: the rows come in marked "Registered", so they are
told apart from freshly collected traffic, and a multi-port cell is split
back out. That lets you reconcile what is already registered against what a
new scan found - the review checks then show traffic with no matching
registration, and registrations nothing is using.


READING AND TRIMMING THE REGISTER

The table scrolls sideways; the tick box and row number stay pinned to the
left so a row can still be identified far along. Addresses, hostnames and
the description are wide enough to read in full, and hovering a cell shows
its whole value where the text is longer than the column.

"Hide addresses", under the filters, leaves rows out of the view:

    an address                10.20.99.99
    a network                 172.22.60.0/24
    a hostname, long or short scanner99 matches scanner99.range.mil
    a wildcard                scanner*, *-test

A row is hidden if either end matches, since a scanner or monitoring host is
worth leaving out whichever direction it appears in. The count beside the box
says how many are hidden.

Hiding is only a view. "Remove hidden" deletes those rows for good - useful
for stripping a vulnerability scanner or backup agent out before export. It
asks first, and the rows come back if you import the same files again.


WHAT THE eMASS TEMPLATE NEEDS FROM YOU

The export matches the PPSM Boundary Information Import Template exactly:
the same 21 columns in the same order (A-U), the same header block, and the
Glossary and Instructions sheets alongside. Its own instructions say EVERY
FIELD EXCEPT PURPOSE IS REQUIRED, so anything the collection cannot observe
has to come from you. Most is set once and applies to every row.

SET ONCE, UNDER SETTINGS

  DNS domain            fills Source FQDN and Destination FQDN. A short name
                        plus your domain makes the fully qualified name the
                        template wants. Collecting the DNS zones is better;
                        this covers what they miss.
  Physical location     fills Source / Destination Physical Location or Cloud
                        Service Provider for anything inside your ranges.
  External label        the same two columns for outside addresses - a cloud
                        provider name, or something like External (non-DoD).
  VPN Tunnel Type when  fills that column on ordinary traffic. Blank by
  there is no tunnel    default; set N/A if your reviewer wants it filled.
  Internal boundary     the template has no plain "Internal", so internal
                        traffic exports as an Internal Use Only boundary,
                        18 by default.

FILL IN THE SYSTEM HEADER

Open "eMASS template header" under System Identification. None of these can
be derived from traffic:

  Exported By, Office / Org, Information System Owner, System ID, DITPR ID,
  POC Name, POC Phone, POC E-Mail, Date Reviewed / Updated, Reviewed By

FILL IN PER ROW

  Purpose   the one field the template marks optional, and the one a
            reviewer reads first: why the flow needs to exist. Select
            several rows and use Bulk apply where they share a reason.

Everything else is filled from what was collected. On export the tool names
any required field still empty and how many rows it affects.

DO NOT RESTRUCTURE THE WORKBOOK

The importer reads columns by position. The template's instructions say not
to delete columns or sheets, remove the classification label, or add
columns. The export respects the character limits it sets - 20 for Port and
Protocol, 40 for Application/Software Record Name, 500 for Source and
Destination, 750 for the FQDN and IP fields, 1500 for the location fields,
1000 for Purpose - and truncates rather than letting a row be rejected.


REVIEW CHECKS
-------------

    Must fix      no boundary; destination port in an ephemeral range; no
                  CAL/VA reference; anything marked Red or Banned; observed
                  traffic with no rule behind it
    Should fix    found by an uncredentialed scan (its port list may be
                  incomplete); no data service; no assurance category; no mission
                  justification; HTTP/HTTPS on a non-standard port (needs an
                  NSPU exception); B13/B14 with no waiver noted; a rule
                  permitting traffic that was never seen
    Worth a look  unnamed internal destinations; duplicate registrations

Export Findings writes the list to CSV with the offending rows attached.

Rule coverage (same card)
    Every observed flow is read against the imported ruleset on all four
    of source scope, destination scope, protocol and port (a single port,
    a range, a list, or blank for any) - not just the port, which would
    let any 443 rule anywhere "cover" every HTTPS flow. Run Coverage
    shows:
      - flows with no permitting rule, partly covered (a consolidated row
        where only some ports have a rule), or matched only by a deny
        rule ("denied but seen")
      - permit rules no flow ever used
    Coverage Report writes one CSV: every flow with the rule(s) that
    permit it, then every permit rule with the number of flows that used
    it. It needs both a ruleset (ACL, object-groups, FMC/Palo policy
    export) and observed traffic in the register.

eMASS export settings (Settings > eMASS template)
    VPN / Encrypted Tunnel Traffic   per row (derived from the boundary), or
                                     Yes / No for the whole export; a tick
                                     box applies it even over per-row values
    VPN Tunnel Type                  one of the template's Glossary values
                                     (AF VPN, GRE Tunnel, JRSS RA VPN,
                                     Type-1 Encrypted Tunnel, ...) written
                                     where a row has none - or to every row
                                     with the overwrite box; never forced
                                     onto a row whose VPN traffic is No
    Source / Destination Physical    the location written for our own
    Location                         addresses at each end (an address
                                     outside the enclave gets the external
                                     label); falls back to the enclave
                                     location
    One row per port                 ON by default: a port is listed ONCE on
                                     the sheet. TCP and UDP on the same port
                                     are one row reading "TCP/UDP"; a port
                                     seen both ways is "Bi-Directional"; a
                                     port seen across more than one boundary
                                     carries them semicolon-joined (the
                                     template's Instructions allow it).
                                     Every service, application, source and
                                     destination seen on the port is joined
                                     in, each named once; a register row that
                                     Consolidate joined ("80; 443") is split
                                     back so each port lands in exactly one
                                     exported row. The working register keeps
                                     its per-flow rows; only the sheet is
                                     shaped.
    IP addresses only                ON by default: no hostnames in Source /
                                     Destination; a name sitting in an
                                     address cell is swapped for its address
                                     from the DNS/AD/scan inventory, and the
                                     FQDN columns carry the address. A name
                                     no source can resolve is left in place
                                     and the export says how many there are.
    Order by port                    ON by default: rows run from the lowest
                                     port to the highest.
    Purpose on every row             ON by default: a row with no Mission
                                     Justification gets a statement built
                                     from the service, both ends and the
                                     port, so column U is never blank. A
                                     written purpose is always used as is
                                     (any [DRAFT] marker is removed).
    Per-row values win unless the overwrite boxes are ticked. Bulk-apply
    in the register can set Source/Destination Physical Location, VPN /
    Encrypted Tunnel Traffic and VPN Tunnel Type on selected or filtered
    rows, with the tunnel type chosen from the Glossary list.

Mission Justification drafts
    Under Fill In, "Mission Justification (draft from service)" is OFF by
    default. Tick it and rows with no purpose get a sentence built from
    the service, the two ends and the port - e.g. "Required for directory
    lookup and authentication over TLS (Lightweight Directory Access
    Protocol over TLS (LDAPS)) from ws01.lan to dc01.lan on TCP 636.
    [DRAFT - confirm the mission need and edit before submission]".
    It is never written by the automatic pass, and the review checks flag
    any row whose purpose still carries the [DRAFT] marker, so boilerplate
    cannot slip into the submission unnoticed.


COMPARE WITH PREVIOUS REGISTER
------------------------------

Load the register you submitted last time - the allow.xlsx the builder
wrote, an eMASS PPSM export (CSV or workbook), a register CSV, or a saved
session - and the builder compares it with the current register:

    Added      in the current register, not the previous one
    Removed    in the previous register, not seen in this run
    Changed    in both, but Data Service, Boundary, Direction, Type,
               Application, VPN, Purpose or a hostname differs

Both sides are compared flow by flow, so a consolidated "80; 443" row in
last quarter's file is matched against the two separate rows here, and a
service written as a code then and as a name now is not a change. Firewall
rules are evidence, not entries, and are left out. Diff Report writes the
three lists to CSV. Mark Registered / New sets Status on the current rows:
Registered where the previous register already carried the flow, New where
it did not - so what you submit is the delta.


EXPORTS
-------

  eMASS Import (allow.xlsx)  the submission workbook: the PPSM Boundary
                           Information Import Template, 21 columns A-U in
                           the template's order, with its Glossary and
                           Instructions sheets. Boundary, Direction, Type,
                           the two Connection Logical Point columns, VPN
                           Tunnel Type and VPN / Encrypted Tunnel Traffic are
                           Excel dropdowns, wired through named ranges so they
                           work in every version. Protocol is normalised on the way in and out, so a scan that reports "?" or an IANA number (6, 17) becomes TCP, UDP or blank rather than a stray character.
  Register (.xlsx / .csv)  the full working register, including columns
                           eMASS does not take
  Boundary diagram         SVG or PNG, drawn from the register itself
  Review findings (.csv)   every outstanding item with its rows
  Session (.json)          everything, including the host inventory

Register exports fold dashes, curly quotes and bullets to plain ASCII,
because they render as "?" in Excel on many desktops. Boundary values are
stored as bare codes for the same reason. The eMASS template always keeps
its exact official wording, since the template requires it.


SETTINGS
--------

Most of these can be left alone. Worth knowing about:

  IPv4 only                on by default. Any IPv6 row is set aside on
                           import and the count is shown. Turn it off only if
                           the enclave genuinely runs dual stack.
  Internal ranges          extra CIDRs counted as inside the boundary, on
                           top of RFC1918. Set this if your enclave uses
                           public or otherwise non-private space, or
                           identification coverage reads low for no reason.
  Custom service names     9997 = splunk-forwarder, or TCP/8443 = vendor-gui.
                           These override the built-in port table, so your
                           own applications get named instead of showing a
                           bare port. Worth setting up early.
  Subnet to enclave map    optional. Without it, the enclave column falls
                           back to the observed /24.
  Minimum packets per flow the quickest way to strip scan noise out of a
                           large capture. Three or five removes single-packet
                           probes.
  Max packets to read      keeps the browser responsive on very large
                           captures.
  Well-known port ceiling  when nothing says which side opened a connection,
                           the better-known port is treated as the server.
  Custom boundary tags     add your own alongside the built-ins, for example
                           a cross-domain solution.
  Simple mode              on by default. Hides the advanced panels; untick
                           at the top for the endpoint list, review checks
                           and per-field controls.


TROUBLESHOOTING
---------------

A file imports as zero entries
    Read the import line. It names what the file was taken to be and why it
    gave nothing. Usually the wrong export - nmap normal output instead of
    -oX XML, or a Tenable HTML instead of .nessus.

An Excel file is refused
    Older binary .xls cannot be read. Open it in Excel, save as .xlsx.

A PDF gives nothing
    Probably a scan or image export with no text in it. Export the original
    instead. For a firewall policy, a CSV export is the most reliable form.

Hostnames are missing
    Add a name source, ideally the DNS zones, forward and reverse. Names are
    applied to every row whenever a new source arrives, so importing one
    later fills in rows that are already there.

Internal traffic shows B13 or B14
    The enclave uses non-RFC1918 space. Add it under Settings -> Internal
    ranges and import again.

Client and server look backwards
    The data had nothing to say which side opened the connection. Fix the
    rows with Bulk apply; the ephemeral-port check flags the likely ones.

Shows "N entries, 0 shown"
    A filter is hiding the rows. Clear the search box and the dropdowns.

Nothing happens when you drop a file
    Not a real browser tab. A preview pane, document viewer or Protected
    View will all do this. Check for file:// in the address bar.

"Could not be read"
    File is locked, open elsewhere, or blocked by endpoint policy. Copy it
    to a local folder you own.

A large capture is slow
    Lower Max packets to read and raise Minimum packets per flow.

Anything else
    Run Self-Test. All green means the tool is fine and the input is the
    problem. Red: note the browser and which checks failed.


TRYING IT OUT
-------------

Unzip the samples and drop the whole folder onto the tool without
configuring anything. It covers every supported format: flow data, firewall
rules, FMC reports, Excel, PDFs, and name sources including forward and
reverse DNS zones.

The register comes out with every internal address named, boundaries
derived, repeat sightings merged, and the review checks listing what a
person still has to decide. One endpoint stays unnamed on purpose - the
firewall's own VPN interface, which appears in no name source - and the
external destinations are documented by service and purpose rather than by
hostname, so they are scored separately.

Everything in the samples folder is invented for demonstration. None of it
came off a real network.


A FEW THINGS WORTH REMEMBERING
------------------------------

The tool assembles a register. It does not certify compliance: the accuracy
of the inputs, and the boundary and assurance analysis, remain the
assessor's responsibility.

Every row records the host the data came from, so an entry can always be
traced back to the sensor, firewall or workstation that observed it.

Save the session before closing the tab. The browser keeps nothing by
itself.
